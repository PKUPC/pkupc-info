# 执笔成谜题目迁移

这是项目内的通用 Agent Skill；路径相对仓库根目录，无需特定模型、飞书登录或插件。只处理《执笔成谜》，不因文章涉及纸笔就纳入《谜协严选》或 PKU Puzzle Cup。

## 准备与来源

先读根目录 `AGENTS.md`、`README.md`、`CONTRIBUTING.md`，确认分支和已有改动。完整读取 [SOP 文字版](references/lark-sop.md)，再读 [项目适配与离线来源说明](references/editorial.md)。SOP 是历史参考，用户要求和当前组件事实优先；保留原题事实、原文术语与署名。

接收用户指定的题目清单 Markdown 和 `zhibi-archive` 路径。本次用户清单已保存在 [搬运对照表原文](references/migration-status.md)，后续用户提供更新版时以新版核对。清单决定迁移范围，归档提供来源证据；找不到清单时先清点归档并报告缺失，不把归档清单当作用户附件，也不宣称完成全部题目。若用户明确允许按归档范围执行，则记录这一范围变化。

开始页面修改前，按 AGENTS 保存现有页面和代表性交互的截图。用项目固定的 Node、pnpm 安装锁定依赖。不要修改归档源文件或将整套离线网页、脚本和公共素材复制到站点。

## 清点、编号与解析配对

建立可续作对照表（建议放在本地 `maintenance/zhibi-migration/`），每项至少记录：

- 清单/归档序号、原题名、日期、原文 URL、来源目录、目标 slug。
- 首发题目、规则/示例、做题链接、提交说明、答案、解析、勘误的具体来源与位置。
- 出题作者、解析作者，题图/解图/步骤图的顺序和原图到目标文件的映射。
- 状态：已有且核查完整、可迁移、缺解析、缺素材、答案待确认、待验证、已完成、勘误已合并。

以原文 URL 的 `__biz/mid/idx/sn` 识别文章，题名和北京时间交叉核对。清单序号、合集序号和站点 `zhibi-NNN` 编号不能默认相等。检查已有 slug 和正文再决定编号；生成器会覆盖同名文章，目标存在时禁止直接生成。

解析通常在后续推文结尾，必须按解析段落的题名、盘面和规则配对，不能机械取下一篇。首篇可能包含上一批末题解析；跨季、停更、特殊篇也须逐题确认。本批末篇即使提供前题解析，也不代表它自身已有解析。同名特别篇按年份、日期和 URL 分开核查，读正文后判定是否含谜题/多题，不仅根据清单的概括分类排除。

原则上只搬运正式解析已发布的题目。解析专篇合并到原题页；勘误按原文明确指向的题目应用，注明更正内容和来源，不凭勘误的清单序号生成空谜题页，不自动将后续编号减一。

原文明确不设置验证的独立特别篇不添加 `<AnswerCheck>`，不编造提交格式，也无需提取口令供公众号验证。若用户明确要求迁移尚缺正式解图的特别篇，可先迁入题目、规则和做题链接，记录缺解析的状态；不生成空解答或空步骤组件。有正式解图但没有步骤文字时，仅保留解图，不补写解析。特别篇以原图标号和年份区分，不能把归档序号强加为正式题号。

## 读取离线素材

按适配说明读取 `manifest.json`、文章 `metadata.json`、`original.html`、`index.html` 和 `assets.json`。静态解析正文 `#js_content`，保留文字、段落、表格、链接、图片说明及其顺序；不要执行归档 JavaScript。

通过 `data-src` / `src` 和 `assets.json` 对应真实正文素材，检查图片可解码、内容正确且无遗漏。题图、规则样例、最终解、步骤图和后记图分别归类；合集封面、头像、二维码、播放器及页面装饰不作为题图。

`partial` 可能仅表示公共播放器资源失败，不能据此否定题目包；正文关键图片缺失则记录阻塞。不要为了消除公共素材报错重复下载已知失败资产。

做题链接可能只在“阅读原文”的 `msg_source_url` 中。仅静态提取字符串并解码 HTML 实体及 JavaScript 字符串转义，保留完整片段和参数，禁止 eval 或执行脚本。找不到链接不生成空链接，记录缺项。

## 编排题目页

以 `scripts/templates/zhibi-000.mdx` 和相近的已迁移题为骨架，按 SOP 命名到 `content/wechat-official-account/zhibi/`。实际适配和多解示例见 editorial.md。

1. 填写真实标题、slug、出题作者、`zhibi` 和全部作者标签、北京时间日期；不沿用模板里的作者或时间占位值。解析作者在解答组件单独署名。
2. `truncate` 前放原文主题机制、期次/题型说明、题图及必要图注；之后放纸笔规则、规则示例、做题链接、提交格式及答案验证。隐藏规则仍需折叠，不能提前泄露。
3. 将公众号私信提交格式转换为网页输入说明，明确保留行列、方向、取个位、区域/长度等提取规则。区分公众号口令前缀和实际答案；依据原文及现有站点约定确定是否保留前缀，不自动删去可能属于答案的字母。
4. `<AnswerCheck>` 使用 `mitiType="zhibi"`。固定答案为字符串；双解/多解用答案对象，各正式解保留 `type: 'CORRECT'`，按原文区别反馈。中间结果只有明确证据时才设为 `MILESTONE`。保留示例中的前导零；示例不等于正确答案。
5. 答案有明确原文或用户提供的验证证据时直接使用；只有解图时按提交规则从正式解提取并逐格复核，记录提取过程。将识别值、提取明细以及带原公众号口令前缀的完整提交串发给用户，由用户在公众号验证；在收到验证结果前标为“图像识别，公众号待验证”，不得称为已获公众号确认。图不清楚、多个解的提取相同或提取规则含糊时说明无法识别的位置，请用户人工介入，不凭题名/示例猜答案。未知答案不得放空验证器或宣称已完成。不得自行向公众号发消息。
6. 最终解放在 `<Solution author={'解析作者'}>` 内；A/B 等解图及步骤分别保留，禁止将多个规则/盘面合并成单解。步骤使用 `### 步骤解析`、`<details>` / `<summary>查看步骤解析</summary>` 与 `<Carousel arrows infinite={false}>`；每一步用 `<CarouselInner>`，其中图片用静态 `require(...).default`，强调用 JSX。
7. 保存原有解析文字、步骤、评价和相关后记图，不擅自补写作者点评。不搬运首解祝贺文案（例如“祝贺 XXX 成为第一个完成的玩家！”）及对应玩家排行榜，无论排行榜为文字、表格或图片；相关图片也不复制到站点。与本题无关的公告、推广、下期预告可省略；判定与解题有关的内容不能省略。仅处理 MDX 所需转义，避免数学符号被误识别为标签。

资源尽量转成 WebP；转换后目视确认细网格、小字、颜色和透明区域，清晰度不足时保留原格式。按 SOP 使用题图、`-rule`、`-sol`、`-sol-1`、`-meme-1`；多解用 `-solA` / `-solB` 并独立编号。不可只更改文件扩展名。

## 验证、交接与迭代

迁移后先逐题对照来源，核查规则、提交说明、答案提取、署名、勘误、全部图片及步骤顺序。查找残留占位符、空链接、未定义作者/标签和失效资源引用；仅格式化本次文件。

执行 `pnpm check`、`pnpm build`、`GITHUB_PAGE_MODE=true pnpm build`。页面验证按 AGENTS 的桌面/窄屏、浅色/暗色、基准路由与交互矩阵进行；新增页逐题核对图文和答案，代表性复杂页覆盖双解/多规则、步骤切换、折叠、错误与全部正确答案、历史提交。同时检查 `/pkupc-info/` 下资源可用。动画和图片稳定后保存截图，不用 DOM 尺寸代替视觉证据。

如果正文图片没有预览能力，如实记录当前页面行为；不要为满足检查悄悄扩展公共组件。不能运行的检查标记为未执行或失败，并说明原因，不宣称远程 CI 通过。

在对照表记录验证和截图路径后才能标为已完成。交接列出完成/合并勘误/搁置项、文件与验证结果；未获授权不提交、推送、创建 PR 或部署，也不向公众号发送消息。

首次执行若发现规则导致遗漏、错误配对、答案错误或不合适的页面编排，先根据具体失败更新本 Skill/适配说明，再重做受影响题目并复核。将执行中学到的可复用约束和单次批次记录分开，不把未经验证的猜测写成通用规则。
